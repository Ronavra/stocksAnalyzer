# Research reliability

Apply `services/api/sql/research_reliability.sql`, `services/api/sql/price_session_quality.sql`, `services/api/sql/company_disclosures.sql`, `services/api/sql/research_completion.sql` and `services/api/sql/recommendation_cadence.sql` (in that order) before deploying this revision to a new database. They have been applied to the existing hosted project.

Recommendation publication uses one database transaction and a global publication advisory lock. A new group of up to five qualifying stocks is published on Sunday, Asia/Jerusalem, for the coming week using the latest validated market close (normally Friday, or Thursday when Friday is a market holiday). The database allows only one group per Sunday week, across all policy versions, including zero-pick cash decisions. Holidays do not postpone Sunday selection. Missing/stale market dates block publication. The Sunday workflow runs at 08:17 with a 12:17 retry; daily GitHub and Windows cycles can also publish on Sunday after refreshing research sources. Ranking code pushes and manual ranking previews never publish recommendations. The separate 5/10/20-trading-day evaluation horizons do not create additional groups. A completed group, including a zero-pick decision, is immutable. `--force` cannot bypass Sunday or replace completed decisions; use `--dry-run` to inspect a different selection. Incomplete legacy publications can be replaced only when unevaluated and on the same policy version. Evaluated legacy data requires explicit recovery. The pre-fix 2026-10-05 group remains frozen in history; the next selection is Sunday 2026-10-11 using the latest close. Legacy Saturday freezes count toward the following Sunday's group. Publication time and the market-close date are separate: the displayed price date can be Friday even though recommendations were published on Sunday. GitHub and local-host availability can delay a scheduled attempt; no successful publication is claimed before its transaction completes.

Prices are deduplicated by company/session with Twelve Data preferred over FMP. Labels use the SPY session calendar and require an exact stock close at the target session. The lightweight price_history_gaps(p_since,p_until) audit checks recent internal holes as well as the latest date; a repaired stock gets a historical feature rebuild. `price_session_quality(p_since)` and `repair_price_feature_labels(p_since)` process 30-day feature windows, including additional future bars to mature their labels. Iterate in 30-day steps for full-history checks. Missing provider bars remain missing, including historical suspensions; they are not extrapolated.

`Research History Repair` performs the initial idempotent repair under the shared market-data concurrency group. It never regenerates completed recommendations. Its revision/status and bounded window results are stored in `pipeline_runs`.

Daily scheduling is 08:00 Asia/Jerusalem. GitHub may start a scheduled workflow late. One workflow retries a failed market stage once, with a smaller provider request budget; success/active-run gating avoids another successful daily refresh on the same Israel date. A running attempt older than 195 minutes can be retried. Manual `force` is an explicit override. The dashboard marks an unfinished daily update overdue after noon and shows its last market close. A start more than 60 minutes after 08:00 and a successful completion after noon remain visible after success; Actions also records them in the run summary. A separate read-only Daily Update Monitor is scheduled at 12:17 Israel time and fails when the noon deadline was missed, even if the data workflow never started. Its separate concurrency group avoids waiting behind ingestion. GitHub schedules remain subject to scheduling delays. An independent Supabase `pg_cron` job checks the noon deadline hourly at minute 17 and records exactly one result per Israel date; it works even when Actions does not start. This records deadline evidence and does not initiate ingestion or send notifications. A database claim prevents concurrent GitHub/local market refreshes. For an 08:00 trigger independent of GitHub, install `scripts/install_windows_schedule.ps1` on a Windows host with Israel Standard Time, the API virtual environment and its existing `.env`. The host must be running and the installing user signed in. The task runs the full gated daily cycle, starts missed tasks when possible and ignores overlapping task instances; it cannot guarantee availability when the host is offline. `/health` is process liveness; `/ready` checks database connectivity.

Financial versions are append-only observations with actual `observed_at`. Initial rows are marked `baseline_observed_now`; they do not retroactively certify old backtests. The financial parser recognizes both capital-lease and finance-lease debt tags, combines reported DebtCurrent with noncurrent debt without counting current maturities twice, and retains missing components as unknown. Reported long-term-only totals retain their proxy provenance and are excluded from the net-debt factor. Supplemental balances use explicit equity/assets/debt tags; bank ROE requires current and year-earlier equity and uses their average. The bank profile adds ROE and CET1; reported Tier 1, total capital and leverage ratios are shown separately. Capital tags accept consolidated or explicitly standardized capital contexts; generic custom tags and segment facts are excluded. When the latest TTM remains behind the filing, it can recover up to five official consolidated filing instances from the preceding 640 days, stopping once freshness is verified. Recovery errors and accession numbers remain in the audit. Field coverage is still incomplete, especially custom cash-flow components, unavailable bank capital tags and companies with a new legal entity or a fiscal-year transition. Missing values are not zeros. Eligibility continues to enforce financial freshness and weighted coverage, with the user's fixed 45/35/10/10 weights.

Expected earnings dates/time are collected within 5/10/20 market sessions. The v3 fixed policy excludes candidates with an expected report within the primary five-session execution horizon (including the next-session entry); it displays longer-horizon risks. Dates can change. Append-only earnings versions preserve expected dates and later revisions from the actual observation time; their baseline is observed now. EPS forecasts, analyst recommendation consensus, corporate guidance and news are separate data layers. Upcoming earnings events already contain EPS consensus for most companies; their coverage is audited separately from the sparsely populated standalone forecast table. Thin/stale consensus remains neutral. News ingestion saves provider headlines, links, publication and first observation times, and provider-supplied sentiment only when present. Guidance ingests append-only vendor revisions and explicit annual numeric ranges from official SEC releases/exhibits, preserving fiscal period, accounting basis and evidence. The SEC parser deliberately leaves ambiguous tables, quarterly ranges and withdrawn guidance unknown. Optional sources run independently; a failed subscription or source remains visible as partial collection and does not erase successful sources. Unavailable guidance/news must not be described as complete data. Free SEC 8-K/6-K disclosures are saved from the already-requested submissions feed with their actual first-observed timestamp; they remain distinct from news articles, inferred sentiment and parsed guidance.

The live scorecard measures equal-weight **weekly cohorts**, separated by frozen policy version and including cash weeks. Partial/maturing cohorts are not included. Net returns retain the original execution policy and costs. Overlapping horizons are not independent observations. The current policy has no validated predictive advantage until enough new forward outcomes exist. The financial comparison now replays only actually observed financial and earnings versions, analyst captures and recorded S&P membership intervals. Pre-archive weeks are excluded, not labelled cash. Historical sector classifications and original pre-archive source releases remain unavailable. The separate v5 learned model automatically fits internal feature weights, tests feature groups using the middle chronological period and reserves the later period for its existing promotion gate. The v5 model also uses recorded membership at each sampled date; it does not train on today's survivors as if they represented the old index. Its existing fit requires at least 120 sampled dates and adequate labelled rows. New financial, earnings, guidance and news families require at least 26 sampled observation dates, including 26 before the later selection period, before promotion. The new archive is too young for this validation and forecasts remain unavailable until sufficient real history exists. Successful validation can publish 5/10/20-session company forecasts; failed or sparse validation publishes none. Return forecasts additionally require beating the return-error baseline. This does not change the fixed 45/35/10/10 recommendation weights or prove an advantage from young observation history.

The web app uses pinned Next.js/React dependencies and `npm ci` with a committed lockfile (Node 20.9+, CI Node 22). Data-loading failures have explicit messages; they are not rendered as an empty successful stock list. Visible dashboards refresh every five minutes or on demand.
